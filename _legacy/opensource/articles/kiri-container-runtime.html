קונטיינרים בלי המשקל העודף: Kiri מנסה להחליף את Docker Desktop

מנוע קונטיינרים צעיר שנכתב ב־Rust, מדבר בשפה של Docker ומנסה להפוך את סביבת הפיתוח המקומית לקלה ומהירה יותר — בלי לדרוש מהמשתמש ללמוד עולם חדש.

יש רגע מוכר למפתחים רבים: רוצים להריץ שירות קטן, מסד נתונים או סביבת בדיקה מקומית — ובשביל זה מפעילים מערכת שלמה שמרגישה כבדה בהרבה מהמשימה עצמה. Docker Desktop הפך את העבודה עם קונטיינרים לנוחה, אבל הוא גם מגיע עם מכונה וירטואלית, תהליכי רקע, צריכת משאבים ושכבת ניהול שאינה תמיד בלתי מורגשת. Kiri הוא ניסיון צעיר ומעניין לפתור את הפער הזה: לשמור על הממשק שמפתחים כבר מכירים, אך לבנות מתחתיו מנוע אחר.

הרעיון: להחליף את המנוע, לא את שגרת העבודה

Kiri כתוב ב־Rust ומציג את עצמו כתחליף קל ל־Docker Desktop ול־OrbStack. נקודת המפתח היא תאימות לממשקי Docker: הוא מדבר את Docker Engine API, ולכן פקודות docker, קובצי Compose וכלי buildx יכולים לעבוד מולו באמצעות הקשר (context) ייעודי בשם kiri. במקום להחליף את כל כלי הפיתוח, Kiri מבקש להיות מנוע נוסף שאפשר לבחור בו.

ההתקנה יוצרת את ההקשר הזה, ואז אפשר להריץ, למשל, docker --context kiri run --rm alpine echo hello. גם docker compose יכול להפעיל שירותים, והפקודות של Kiri עצמה מוסיפות יכולות כגון אשכול Kubernetes יחיד, מכונות Linux ושיתוף פורט מקומי החוצה.

מה קורה מתחת למכסה המנוע?

הארכיטקטורה שונה מעט בין מערכות ההפעלה. ב־macOS וב־Windows קונטיינרים של Linux זקוקים לסביבת Linux, ולכן Kiri מפעיל מכונה וירטואלית קטנה. ב־Linux הוא יכול לעבוד ישירות מול ליבת המערכת. בתוך סביבת האורח פועל agent קטן שמקבל פקודות מהמנוע המארח ומקים קונטיינרים באמצעות מנגנוני הליבה — namespaces,‏ cgroups ו־clone3.

התרשים שהפרויקט מציג הוא פשוט למדי: לקוח Docker או Compose שולח בקשה דרך Docker Engine API; הדמון של Kiri מנהל את המכונה הווירטואלית ומעביר פקודות לסוכן שבתוכה. לפי תיעוד הפיתוח, המימוש אינו נשען על שרשרת הרכיבים הרגילה של dockerd,‏ shim ו־runc, אלא על סוכן משלו. זו אינה רק עטיפה גרפית ל־Docker: מדובר במימוש עצמאי של חלקים משמעותיים ממחזור החיים של קונטיינר.

הבטחת הביצועים — ומה צריך להבין ממנה

ה־README מפרסם מדידות מרשימות: בהרצת קונטיינר קצרה דרך Docker Engine API, הפרויקט מדווח על חציון של כ־2.55 מילישניות ב־Kiri לעומת כ־213 מילישניות ב־Docker Desktop וכ־380 מילישניות ב־OrbStack, בתנאי הבדיקה המתוארים במאגר. הוא גם מפרסם מדידות Linux ו־Windows נוספות.

אלה נתונים של הפרויקט עצמו, ולא בדיקה בלתי תלויה. חשוב גם לא להכליל ממדד יחיד: זמן יצירת קונטיינר אינו שקול לביצועי רשת, אחסון, בנייה או עומס מתמשך. באחת מטבלאות Linux של הפרויקט, למשל, Kiri מציג יתרון בכמה מדדים אך נופל בהעברת תעבורה דרך פורט מפורסם. לכן יש להתייחס למספרים כאל הזמנה להריץ benchmark משלכם, לא כהוכחה ש־Kiri מהיר יותר בכל מצב.

לא רק קונטיינרים

מעבר לתאימות Docker, Kiri מציע ממשק שולחני לניהול קונטיינרים, תמונות, volumes ורשתות; שמות מתחם מקומיים בסיומת .kiri.local עם HTTPS דרך רשות אישורים משלו; ייבוא של תמונות, volumes וקונטיינרים מ־Docker Desktop או OrbStack; וכן פקודות ליצירת מכונות Linux ואשכול Kubernetes מקומי. חלק מהיכולות מסומנות כבטא, ובהן העברת התקני USB לקונטיינרים.

עוד פרט ראוי לציון הוא מנגנון העדכונים: לפי התיעוד, Kiri בודק חתימות של גרסאות חדשות לפני התקנתן. גרסה 0.2.2, שפורסמה ב־19 בנובמבר 2026, כללה גם תיקוני אבטחה חשובים — בין היתר צמצום הגישה של מכונה וירטואלית לתיקיות מארחות, בדיקות מחמירות יותר ל־mounts והחלת seccomp. עצם קיומם של תיקונים כאלה הוא תזכורת לכך שמנוע קונטיינרים הוא רכיב אבטחה, לא רק כלי נוחות.

למי זה מתאים — ולמי כדאי להמתין?

Kiri מעניין במיוחד מפתחים שמריצים כמה שירותים מקומיים, משתמשים ב־Compose ורוצים חלופה פתוחה למוצרי desktop מסחריים או כבדים. הוא תומך ב־macOS 14 ומעלה, Windows 10/11 דרך WSL 2, והפצות Linux שונות. מנקודת מבט של אימוץ, היתרון הגדול הוא האפשרות לבדוק אותו לצד סביבת Docker קיימת, בלי לשנות מיד את כל הפקודות וההרגלים.

אבל זה עדיין פרויקט צעיר: גרסת 0.2.2 היא גרסת טרום־1.0, ולכן יש לצפות לשינויים, פערי תאימות וקצוות לא מלוטשים. לפני שימוש בפרויקטים קריטיים כדאי לעבור על רשימת היכולות והמגבלות, לבדוק workloads אמיתיים, ולוודא שתכונות חשובות — networking,‏ volumes,‏ buildx, הרשאות ואבטחה — מתנהגות כפי שנדרש. בנוסף, שם המותג והלוגו אינם כלולים ברישיון הקוד, אף שהקוד עצמו מופץ תחת Apache-2.0.

השורה התחתונה

Kiri מנסה לעשות משהו שאפתני: לא להמציא דרך חדשה לכתוב קובצי קונטיינרים, אלא להחליף את התשתית שמריצה אותם. השילוב בין Rust, ממשק Docker מוכר, מכונה וירטואלית רזה ומימוש עצמאי של רכיבי הריצה הופך אותו לפרויקט ששווה לעקוב אחריו. הוא עדיין לא תחליף אוטומטי לכל סביבת פיתוח, אבל הוא מציע ניסוי הנדסי מעניין בשאלה עד כמה אפשר לצמצם את העלות של סביבת קונטיינרים מקומית.
